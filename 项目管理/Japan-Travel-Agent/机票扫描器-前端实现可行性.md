# 候选城市 × 日期区间机票扫描器：前端实现可行性

讨论日期：2026-10-03。目标：打开网页时刷新多个出发/目的城市在日期区间内的低价结果，前端排队扫描、显示进度、本地只保存最新成功结果；优先不用个人 API Key，必要时加 Cloudflare 代理。

## 当前结论

GitHub Pages 可以托管界面、TS 构建后的 JavaScript、扫描队列和本地缓存。纯前端数据采集是否成立取决于上游 CORS、认证和响应形态，不能从 MCP 的语言是 TS/Python 推断。

最值得先实验的是从 itamx 拆出 ITA Matrix HTTP 客户端写成 TS。本轮带 `Origin: https://example.github.io` 的 OPTIONS 与实际地点查询都成功，并且返回匹配的 Access-Control-Allow-Origin。地点查询给出 TYO/NRT/HND。这是响应头和 HTTP 测试，**尚未做真实 GitHub Pages 页面浏览器 fetch 端到端测试**。

机票查询第一轮 `sorts=price` 返回业务 input error；改 `default` 后 35 秒超时。最终使用完整 summarizers、55 秒 timeout 成功：PVG→NRT，2026-11-10，单成人经济舱，CNY，返回 7 个 solution、外层/内层 HTTP 200，无业务 error，实际响应 CORS 允许上述外部 Origin，约 36.46 秒。返回汇总最小值 CNY1300 仅作为此轮响应存在的证据，不是最终购买价。多城市、灵活日期和最低价穷举仍未测。

Matrix 使用页面公开应用 Key，不需要注册个人付费 Key，但不等于底层没有 Key。当前首页未直接找到它，测试用了 itamx 仓库的公开 fallback；轮换/获取位置变化会影响客户端。非公开稳定契约，也未独立确认上游授权。

## 候选比较

| 来源 | 能否拆开 MCP | 纯网页前端路径 | CF 路径 | 当前判断 |
|---|---|---|---|---|
| itamx / Matrix | 能，独立 HTTP 客户端 | 有 CORS 正面证据；单程报价已返回，浏览器页面端到端待测 | 可把公开 key 获取/协议适配移到 Worker | 无个人 Key 优先实验 |
| fast-flights | 能，查询编码 + HTML 解析 | Google Flights HTML 本轮无 ACAO，直接读取被浏览器 CORS 限制 | Worker 抓 HTML/解析可实验；原库浏览器特征客户端未必可照搬 | 第二无个人 Key 实验 |
| HasData | 能，REST API 或远程 MCP | MCP 预检允许外部 Origin，但仍需要用户 Key/OAuth | Worker 保存 Key、调用 REST | 有 Key 的简单后备 |
| SerpAPI | 能，直接 HTTP JSON | 不在本轮确认浏览器直连；需私人 Key | Worker 保存 Key、调用 search | 有 Key 的结构化后备 |
| Aviasales | 能，Data API | 本轮 OPTIONS 404，不能据此断言所有 GET 无 CORS | Worker + Travelpayouts token | 近期缓存低价灵感，非实时最低票价 |
| KAYAK | 能拆源码，但含会话 | poll 预检无 ACAO；Cookie/CSRF/浏览器会话阻碍 | 普通 Worker 不等于 Chromium；需单独 Browser Run/浏览器服务 | 不先选 |
| 携程/飞猪、逆向 Skyscanner | 可研究 | 跨域/会话/页面/风控仍需解决 | 代理不自动解决风控或国际搜索 | 暂不作为核心 |

`mode:no-cors` 只会得到 opaque 响应，不能解析航班 JSON/HTML。页面不能任意设置 Cookie/Origin，不能像服务器端脚本一样复制会话请求头。

## 扫描与缓存

用户提出的等待、进度条、本地 store、仅保留最新值足够支撑个人工具。建议集中处理以下几个与结果正确性有关的细节：

1. 单程任务数通常是 出发候选数 × 目的候选数 × 日期数。3×5×30=450 次；平均请求间隔 4 秒，仅间隔就有约 30 分钟，另加网络耗时。往返则要按有效出发/返回日期组合计算，不能拿两个单程最低价等同真实往返票价。
2. 若 Provider 支持 multi-airport/日期灵活窗，优先研究用少量请求生成候选，再精查低价日期。其结果可能经过截断，不保证每一城市日期都有完整最低价；逐格价格表仍需验证覆盖。
3. 任务队列至少区分成功、无结果、失败、未执行；显示“当前已查询候选最低价”和完成比例。未完成不能写全范围最低；扫描时间跨度也会造成报价不同步。
4. cache key 包含 from/to/departure/return、人数、客舱、币种、直飞/转机、销售地区及 provider。只用 date/dst/src 可在固定这些条件的第一版工作，否则会串价。
5. 每项只保存最新成功结果即可，带 fetchedAt 和查询条件。失败时保留旧成功值，标记刷新失败/旧缓存，不能把旧低价作为本轮新价。LocalStorage 存精简结果可行；数据量大用 IndexedDB。
6. 边查询边存，刷新后续跑；避免多个标签页重复扫描。关闭网页后普通前端不能保证继续执行，Service Worker 也不等于可靠长期扫描任务。

随机间隔可以减少突发，不能保证不触发反爬。风控还有 IP、TLS/浏览器特征、会话、行为与请求内容。403/验证码停止该源，429 按 Retry-After 退避；随机抖动用于调度，不作为稳定性的证据。

## 推荐实施路径

先做纯 TS 的 Matrix 单路线、单日期实验：机场查询→单程报价→往返报价→真实页面 CORS→官方页面人工对照。单程 HTTP 报价已通过；继续往返和真实浏览器，再加多个城市和日期窗，不先移植 MCP 层。

若 Matrix 不稳定，使用 GitHub Pages + 一个小 CF Worker；前端继续负责队列、进度、本地缓存，Worker 每次只代理一个查询、适配响应。Worker 没有必要持久化用户业务数据或扫描所有日期。Key 用 Worker secret；固定上游、限制参数与访问，避免公开成任意代理。

付费后备是 HasData/SerpAPI。HasData 文档为每次成功请求 15 credits，450 次=6,750 credits，往返腿/购买选项可能有附加调用；即使愿意等待也不会自动降低每请求成本。SerpAPI 文档声明同参数缓存 1h 内命中不计搜索次数，但扫描新日期仍需计算预算。

普通 Worker 可以做 HTTP 转发和 TS 解析；Chromium 属于单独 Browser Run 服务及相应额度。CF 解决跨域桥接和密钥保管，不保证上游数据可用，也不自动解除验证码/会话限制。
