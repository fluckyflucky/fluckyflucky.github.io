# [杂项] JMdict 词典的 JSON 切片方案

本站的单词卡片之前用 `sql.js` 在前端跑 SQLite 查 JMdict 词典，体验不太好，遂采用切片方案减少单次加载流量。

## 原来的方案

把 JMdict 的日英中词典塞进一个 SQLite 文件（`dict.db`），浏览器先加载 `sql.js` 的 WASM（~650KB），再把整个 db（~98MB）fetch 下来丢给 SQL.js 解析。

98MB 得先全部下载完才能查词，网络差的时候首页一直转圈。加上整库常驻内存，对移动端不是很友好。

而且根本用不到 SQL 的什么高级能力 ，就一个 LIKE 前缀查询加简单的 FTS MATCH，分页更是没有，旧的实现只做了个 LIMIT。`sql.js` 本身也不小，WASM 的加载路径也得专门处理。

为了前缀搜索拉了一整个 SQL 引擎下来，每次都加载一个.db文件，体验太差不值得。

## 新的方案：按读音前缀切 JSON

核心思路很土，但真的有用：把所有词条按读音罗马字的前两位切开，一共几百个小 JSON。

目录结构：

```
public/jmdict/
  examples.json      # 4.6MB，所有带例文的词条（抽出来给单词卡用）
  kanji-map.json     # 汉字 → romaji 前缀的映射表
  ro/
    a.json           # 7.3KB
    aa.json          # 69KB
    ab.json          # 58KB
    ...
    sh.json          # 3.2MB（最大的一个）
    ...
    zu.json
```

生成这些 JSON 的脚本很简单：读 JMdict 的原始 XML → 解析词条 → 用 `wanakana` 把每条读音转罗马字，取前两位当 bucket → 按 bucket 分组写到对应文件。对每个汉字，把它出现过的所有词条的读音前缀收集起来，建立 `kanji-map.json`。整个过程本地跑几分钟，JMdict 词典文件需要更新了重新跑一次脚本就行。

每个 JSON 文件是一个紧凑格式的词条数组，字段名压缩成单字母：

```json
[{
  "k": ["漢字"],       // kanji
  "r": ["よみかた"],    // readings (kana)
  "o": ["yomikata"],    // romaji
  "s": [{               // senses
    "p": ["词性"],
    "e": ["definition"],
    "z": ["中文翻译"]
  }],
  "x": [{               // examples
    "j": "日文例句",
    "c": "中文翻译"
  }]
}]
```

gzip 后最大的 `sh.json` 从 3.3MB 压到 ~888KB，压掉七成多。

## 查询路由

假名和罗马字最简单。取首字符转罗马字（或者输入本来就是罗马字），截前两位，直接定位到对应文件。ねこ → `ne` → `ro/ne.json`，没了。

汉字会麻烦不少。要先查 `kanji-map.json` 拿到这个汉字关联的所有前缀，然后把这些前缀对应的文件全加载进来，在里面找 k 字段匹配的词条。`kanji-map.json` 是离线生成的——扫一遍词库，对每个汉字，把它所有读音的罗马字前两位塞进一个集合。拿「人」来说，一般有ひと、にん、じん三种读法，前缀就是 `hi`、`ni`、`ji`，所以映射是 `"人": ["hi", "ni", "ji"]`。

同一个汉字关联的前缀数量差异很大，中位数 5 个，但常见汉字动辄几十上百——「猫」51 个，「人」132 个，「日」98 个。这意味着首次查一个常见汉字要加载几十 MB 的 raw JSON（人对应约 48MB），gzip 后实传十几 MB。HTTP/2 多路复用不至于排队，而且每个 shard 只加载一次，缓存命中之后就是纯内存匹配，翻页换词都不再产生网络开销。

假名这边只转了首字符的罗马字，大多数情况够用，但拗音（きゃ、ぎゅ 之类）会漏——`きょう` 的首字「き」转罗马字是 `ki`，但实际的 bucket 是 `ky.json`。好在这种情况不多，暂时先这么用着。

文件缓存目前的实现是分两层。内存里一个 `Map`，页面生命周期内有效，毕竟一次会话查不了几个前缀，内存累积不起来。

## 前端搜索流程

```
输入 → 判断类型 → 确定 prefixes[] → for each prefix:
         fetch ro/{prefix}.json （有缓存就跳过）
         → 遍历词条做前缀匹配
         → seen 去重
         → 计数 / 分页截取
```

分页是先扫完全部匹配项拿到 totalMatches，再按页码截当前页的数据。翻页时重新走搜索流程，但因为文件已经缓存了，只是重新做一次内存匹配，还是很快的。

有例句的词条单独抽了一个 `examples.json`（大概5MB），切 tab 的时候加载一次。之后就是随机往外抽，内存里存 6 条，抽到剩两条的时候异步补数据。

单字符输入前缀只剩一个字母，比如a就是`ro/a.json`，慢慢匹配，各文件结果有多有少，但是量级上差不太多。

单个汉字是真麻烦，`kanji-map.json` 救了但代价也在——常见汉字首次搜要拉几十个 shard、几十 MB raw JSON，gzip 后十几 MB，拉完就全缓存了。

拗音假名会漏，首字符转罗马字偷懒的锅，以后再说。全文搜索和 SQL 灵活性都没了，无所谓，查个单词本来也用不上。不存在的 prefix 文件 fetch 不到就跳过。

切换完体感最明显的就是打开不用等了，假名罗马字秒出，汉字首次慢一点之后走缓存。`sql.js` 换成 `wanakana`，依赖缩到大概几十分之一，搜索逻辑从 SQL 拼接变成纯字符串匹配，代码少了一截。
